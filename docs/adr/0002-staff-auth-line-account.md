# 店舗ユーザーの認証にLINEアカウントを使用する

- 文書ID: ADR-0002
- 決定日: 2026-11-08
- ステータス: 採用
- 関連要件: 引き継ぎ資料 8.「店舗ユーザーの認証・認可」（8.1〜8.3）、15.「セキュリティ要件」、19.「受け入れ条件」店舗向け・セキュリティ
- 関連文書: [ADR-0001](0001-architecture.md)「フェーズ2の認証」

---

## 1. 背景

フェーズ2（予約一覧、キャストの呼び予約、来店登録、会計、日次集計）では、オーナー・スタッフ・キャストを
個人単位で識別し、ロール（owner / staff / cast）に応じた権限をサーバー側で判定する必要がある。
呼び判定は「誰が予約を登録し、誰が来店登録したか」に依存するため、共有アカウントや本人性の弱い方式は使えない。

引き継ぎ資料では Google アカウント認証を第一候補、スタッフID＋PINを代替としていた。
フェーズ1の検証で、GAS 標準のユーザー識別は個人 Gmail 間では利用できないことが分かり、方式の再選定が必要になった。

## 2. 検討した選択肢

- **A. スタッフID＋個人PIN**: GAS で PIN をソルト付きハッシュ保存し、セッションを発行する。外部サービスに依存しない。
- **B. Google アカウント（GAS 標準）**: `Session.getActiveUser()` でメールアドレスを取得する。
- **C. Google アカウント（Google Identity Services）**: 管理画面で Google ID トークンを取得し、GAS で検証する。
- **D. LINE アカウント**: LIFF（LINEミニアプリ）で取得した LINE ID トークンを GAS で検証し、`sub` を店舗ユーザーに紐づける。

## 3. 決定内容

**D. LINE アカウント** を採用する。

- 店舗用画面は LIFF（LINEミニアプリ）として LINE 内で開く。
- 毎リクエストで LINE ID トークンを送り、GAS が LINE の検証エンドポイントで検証する（フェーズ1と同じ仕組み）。
- 検証済みの `sub` を `Users.login_identifier` と照合し、`active` とロールをサーバー側で判定する。
- 店舗ユーザーとの紐づけは、オーナーが発行する**1回限り・有効期限付きの招待コード**で行う。
  最初のオーナーは GAS エディタから招待コードを発行して登録する。
- `Users.login_identifier` には LINE の `sub` を保存し、画面には表示しない。

## 4. 決定理由

採用しなかった案:

- **A（PIN）**: オーナーがアカウント方式を指定した（2026-11-07）。加えて、PIN の推測対策（試行回数制限、
  ハッシュ化、セッション失効、再認証）を自前で実装・運用する必要があり、試験導入の予算に対して負担が大きい。
- **B（GAS 標準の Google 認証）**: 個人 Gmail 間では「自分として実行」時にオーナー以外のメールアドレスを
  取得できない。「アクセスしたユーザーとして実行」ではスプレッドシートを全利用者に共有する必要があり、
  「キャストにスプレッドシートを共有しない」（資料 15.）に反する。
- **C（Google Identity Services）**: 技術的には実現できるが、Google アカウントを持たないキャスト
  （iPhone のみの利用者など）にアカウント作成を求める必要がある。OAuth クライアントの設定作業も増える。

採用した案（D）の利点:

- キャスト・スタッフ全員が既に LINE を使っており、新規アカウント作成やパスワード管理が不要。
- 本人確認の仕組み（ID トークンのサーバー側検証）がフェーズ1と共通で、実装済み・テスト済みのコードを再利用できる。
- 端末の LINE ログイン状態に依存するため、PIN の漏えい・使い回しが起きない。

## 5. 影響と注意点

| 対象 | 影響 |
|---|---|
| `Users` シート | `login_identifier` に LINE の `sub` を保存。招待コード用の列またはシートを追加 |
| GAS API | 店舗向け操作すべてで ID トークン検証とロール判定を行う |
| LINE Developers | 店舗用画面の LIFF（ミニアプリ）設定が必要（下記の未決事項） |
| ADR-0001 | 「フェーズ2の認証」を本 ADR で確定 |

注意点・受容するリスク:

- **端末紛失時**: LINE にログインしたままの端末を拾得されると店舗画面を操作され得る。
  オーナーが `Users.active` を `FALSE` にすれば即時に操作できなくなる（毎リクエストで照合するため）。
- **LINE アカウントの乗り換え**: 機種変更で LINE アカウントを引き継げなかった場合、`sub` が変わる。
  オーナーが招待コードを再発行して紐づけ直す。
- **LINE 障害時**: 店舗画面も使えない。試験導入では受容し、紙での記録を代替手段とする。
- **同一人物が顧客にもなる場合**: 顧客（`Customers`）と店舗ユーザー（`Users`）は別管理とし、
  店舗ユーザーであることを理由に顧客予約の扱いを変えない。

未決事項（実装前に確定する）:

- 店舗用画面を、顧客用と同じミニアプリチャネルのサブパスで提供するか、店舗専用のミニアプリチャネルを作るか。

## 6. 代替案への復帰

C（Google Identity Services）へ切り替える場合は、`Users.login_identifier` をメールアドレスに置き換え、
全店舗ユーザーの紐づけをやり直す。ロール判定・監査ログ・業務ロジックは識別子の種類に依存しない設計とし、
認証部分（トークン検証と `Users` 照合）の差し替えだけで済むようにする。
